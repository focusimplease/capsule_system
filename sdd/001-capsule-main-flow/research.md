# 阶段 0（Phase 0）调研：胶囊系统第一版主流程

本文解决规划简报中提出的技术问题。除非后续通过 SPEC 或宪章变更明确修订，否则这里的每项决定都对阶段 1 具有约束力。

## 1. 运行架构与职责边界

**决定**

采用模块化的 Python 3.12 单体，通过稳定 CLI 和基座无关的 Skill 对外提供能力。当前 Agent 基座是运行主控：Agent 负责自然语言和语义理解，Skill 负责交互分流与调用编排，Python 负责输入校验、确定性提取、语义结果校验、最终持久化、策略检查以及所有不可逆操作。第一版不引入 FastAPI、HTML 界面、独立前端、MCP 或特定 Agent Plugin。

**理由**

“CLI 命令 + Skill”是多个 Agent 基座都可以支持的轻量扩展方式。独立 CLI 能隔离 Python 环境，并使会改变业务数据的操作可以直接测试。Skill 是交互与编排方法，但不是业务规则或持久化核心；这个区分可以避免 Prompt 变化绕过确定性约束。对于单用户本地产品，没有必要增加常驻服务。

运行时采用稳定的循环调用链：用户 → 当前 Agent → Skill → `capsule` CLI → Python 确定性步骤 → `next_action` → Agent 语义任务 → CLI 提交结果 → Python 校验并继续。所有往返在同一任务中完成，不保存持久 `operation_id`、待处理 Agent 动作或恢复检查点。

**考虑过的替代方案**

- 特定 Agent Plugin：可以注册原生工具 Schema，但会把应用依赖与某个运行时耦合。
- MCP 服务：提供可复用的结构化传输，但会增加进程和生命周期管理，对第一版没有必要。
- 让模型临时编写 Python 调用或 Shell 片段：不够稳定，也容易绕过校验。
- HTTP 服务或界面：违反已经确定的纯 Agent 产品边界。
- 让 Skill 直接调用大量零散 Python 脚本或内部函数：会把 Prompt 与实现细节耦合，无法形成稳定的版本化工具契约。

**依据与来源**

- 当前安装版本为 `Hermes Agent v0.18.0`，可作为兼容性测试基座；Codex 作为主要开发基座。

- `/Users/apple/.hermes/hermes-agent/toolsets.py` 与 `tools/registry.py` 表明 Hermes/飞书工具集中可以使用 terminal。

## 1A. 产品交付单元

**决定**

本次开发形成一套可以共同运行的源码与开发验证资产，包括 Python 模块、`capsule` CLI、基座无关的 Skill、飞书适配与权限预检、测试和开发验证指南。安装包、安装 Skill、面向用户的环境检查、升级与卸载另行规划。

## 1B. Agent 与 Python 的循环驱动协议

**决定**

通用模型推理由当前 Agent 基座完成，Python 不直接调用另一套通用大模型 API。Python 每次只执行当前可以确定完成的步骤；需要图片理解、主题判断、新旧知识比较或页面组织时，返回结构化 `next_action`。Skill 指导当前 Agent 完成该动作，再通过 CLI 把结果提交回当前任务。

`next_action` 至少包含动作代码、必要上下文引用、结果 Schema 版本和允许的后续动作。Python 拒绝动作不匹配、Schema 不合法、证据引用不存在或违反策略的结果。校验通过后继续当前任务，直到成功、生成审核项、失败或产生新的 `next_action`。`next_action` 不持久保存，也不能用于跨会话恢复。

**理由**

当前 Agent 已经具备模型能力。如果 Python 在内部再调用一套通用模型 API，会产生两套模型配置、上下文、工具权限和错误处理方式。循环协议让 Agent 负责推理、Python 负责校验和约束，同时保持业务核心与具体基座无关。

**考虑过的替代方案**

- Python 一次 CLI 调用内部完成全部流程：除非 Python 自己调用 LLM，否则无法完成中间语义步骤。
- Python 直接调用通用模型 API：形成第二个 Agent/模型运行边界，并破坏基座无关的职责划分。
- 把 `next_action` 持久化为可恢复流程：会引入 Brief 已明确排除的状态管理复杂度。
- 为每个 Python 函数建立一条 Skill 指令：接口数量容易失控，并把内部重构暴露给 Prompt。

**依据与来源**

- 规划简报（Planning Brief）中确认的运行驱动方式。
- [contracts/agent-cli.md](./contracts/agent-cli.md) 中的 `next_action` 契约。

## 2. Agent CLI 契约

**决定**

每条命令使用专属的 Pydantic v2 请求模型，并统一返回带版本的 JSON 结果信封。标准输出只包含结果信封，诊断信息写入标准错误。结果状态只使用 `success`、`review_required` 和 `failed`；`review_required` 是正常的业务终态，不是程序异常。结果信封不得包含持久操作 ID、检查点或恢复位置。审核决定使用稳定决定代码；不可逆决定必须绑定准确对象和本次明确确认。

**理由**

自然语言适合用来理解用户意图，却不适合直接授权任意状态变更。稳定结果信封可以让不同 Agent 基座可靠地区分成功、进入审核、外部依赖失败和策略拒绝。明确对象确认可以避免一句宽泛表达被错误地用于范围更大的删除。

**考虑过的替代方案**

- 只返回退出码和自然语言：无法表达“操作正常完成，但流程暂停等待审核”。
- 每条命令使用不同的响应结构：会迫使 Agent 反复推断字段。
- 使用统一的 `action + payload` 万能命令：会削弱命令级校验和授权边界。

**依据与来源**

- `/Users/apple/.hermes/hermes-agent/model_tools.py` 中的 Hermes 工具处理器会把结构化结果序列化为 JSON 字符串。
- 第一版命令与结果信封的详细契约见：[contracts/agent-cli.md](./contracts/agent-cli.md)。

## 4. 飞书各组件的职责划分

**决定**

- 飞书知识库负责导航以及主题、概念和证据的层级结构。
- 飞书云文档负责长文本：包括可修改的主题页、概念页，以及每份衍生证据对应的一份独立固定文档。
- 飞书多维表格负责终态结构化记录：包括资料索引、最终处理结果、证据与页面关系、审核项、审核决定和规则改进候选。
- 飞书云盘只用于元数据、权限、版本以及经过明确确认后的文本资源删除。
- 不使用飞书附件字段或附件上传 API。

**理由**

知识库节点适合表达层级，云文档适合保存可阅读、可编辑的长文本，多维表格则适合保存字段、筛选条件和对象关系。这种职责划分还能让固定后的证据与会持续修改的知识文章在物理上保持分离。

**考虑过的替代方案**

- 所有内容都放入多维表格：长文本阅读和编辑体验较差，也会受到字段容量限制。
- 所有流程历史都放入云文档：无法可靠地按照审核类型、触发条件或状态筛选。
- 用云盘文件夹代替知识库：知识导航能力更弱，而且会重复知识库已经承担的职责。
- 短证据放多维表格、长证据放云文档：会形成两条权威读取路径。

**依据与来源**

- 飞书云文档能力概述：https://open.feishu.cn/document/server-docs/docs/docs-overview.md
- 知识库节点 API：https://open.feishu.cn/document/ukTMukTMukTM/uUDN04SN0QjL1QDN/wiki-v2/space-node/create
- 当前安装的 `lark-cli` 1.0.68 已提供知识库、云文档、多维表格、云盘和记录操作。
- 详细存储契约见：[contracts/feishu-storage.md](./contracts/feishu-storage.md)。

## 5. 一次性任务与最终写入

**决定**

飞书是唯一的长期业务数据层，第一版不使用 SQLite、outbox、本地状态库或持久化任务队列。一次任务先在当前会话、内存或受控临时目录中完成读取、提取、语义理解、页面组织和全部 Schema 校验，之后才进入最终写入。Base 只保存成功结果、审核项、审核决定、不采纳或终止等终态，不保存 `running`、检查点、恢复位置或重试计划。

**理由**

飞书云文档、知识库和多维表格之间没有共同事务，因此无法在不引入状态管理的情况下提供严格的跨资源原子性。第一版采用“先计算，后提交”缩短风险窗口：先完成全部内容与约束检查，再创建完整证据、更新知识页，最后写入 Base 终态记录，并重新读取关键资源核对结果。写入冲突或部分成功无法在当前任务中安全补偿时，系统生成包含受影响资源、实际结果和建议的新审核项；该审核项是当前任务终态，不是恢复检查点。

**考虑过的替代方案**

- 建立 SQLite 和 outbox：可以增强恢复能力，但违反最新 Brief 对第一版复杂度的限制。
- 边计算边写入：会扩大远端半完成结果的窗口。
- 使用持久暂存区：暂存资源本身就是 Brief 禁止的中间状态。

**依据与来源**

- `lark-cli` 的 Wiki、Docx 与 Base 写入是彼此独立的远端操作，不能形成共同事务。
- Docx 更新可能返回 `partial_success`，因此必须检查结构化结果并进行写后读取验证。
- 飞书频率控制说明：https://open.feishu.cn/document/server-docs/api-call-guide/frequency-control.md

## 5A. 飞书适配器的调用方式

**决定**

Python 飞书适配器调用当前安装的 `lark-cli` 1.0.68，并读取它的结构化输出，完成第一版涉及的知识库、云文档、多维表格、云盘和授权操作。第一版不混用 `lark-cli`、原始 HTTP 请求和官方 Python SDK。如果适配器契约测试证明 [feishu-storage.md](./contracts/feishu-storage.md) 中的某项必要操作无法通过 CLI 完成，应先暂停并修订本 Plan，再决定是否增加另一种调用方式。

**理由**

当前 CLI 已经覆盖所需的飞书产品，并统一处理身份认证。只使用一种调用方式，可以让适配器只有一套错误、凭证和升级边界。如果每个方法都可以临时回退到另一套 SDK 或 HTTP 调用，重试行为和身份归属将很难验证。

**考虑过的替代方案**

- 所有调用都使用官方 Python SDK：可以实现，但会放弃已经确认的本地 CLI 方向，并需要第二套凭证配置。
- 直接调用 OpenAPI：覆盖最完整，但需要自行重复实现认证、分页和错误处理。
- CLI 加静默的 SDK/HTTP 回退：边界最模糊，因此不采用。

**依据与来源**

- 对本地 `lark-cli` 1.0.68 的命令检查确认，它覆盖知识库、云文档、多维表格、云盘、OAuth、记录 upsert/历史、视图和工作流。
- 规划简报（Planning Brief）已明确要求优先使用当前安装的飞书 CLI。

## 6. 飞书身份、事件与并发

**决定**

使用个人用户的访问令牌，并只申请所选 API 必需的最小权限。系统同时校验 API 权限和具体资源访问权限。第一版由当前 Agent 发起命令，不依赖飞书编辑事件。对同一张多维表格串行写入；所有列表和搜索调用都正确处理分页；遇到 429 或多维表格错误 `1254291` 时只在当前任务中进行次数受限的退避重试；更新云文档时必须使用读取内容时取得的版本号。

**理由**

机器人身份可能看不到或不拥有用户现有的资源。核心流程已经由 Agent 发起，因此再加入 Webhook 或长连接事件处理会形成重复入口。带版本的写入可以防止系统静默覆盖用户手工修改或并发修改。

**考虑过的替代方案**

- 机器人身份：适合应用自己拥有的资源，但不适合个人用户已经存在的知识空间。
- Webhook：需要可以从外部访问的服务，不符合当前本地 Agent 架构。
- 无条件覆盖云文档最新版本：可能覆盖本次合并方案从未读取过的修改。

**依据与来源**

- 飞书权限模型：https://open.feishu.cn/document/server-docs/application-scope/introduction.md
- 飞书事件订阅概述：https://open.feishu.cn/document/server-docs/event-subscription-guide/overview.md
- 当前执行 `lark-cli auth status --verify` 返回 `not_configured`，因此配置与授权是明确的前置条件。

## 7. PDF 文字提取

**决定**

使用 `pypdf` 6.16.1，只读取 PDF 中已经存在的文字层。不渲染页面、不提取图片，也不对纯图片页面执行 OCR。扫描版 PDF 如果没有可用文字层，应产生“不完整”的证据结果；核心内容因此无法取得时，生成“处理中断”审核项。提取前或提取过程中必须限制输入大小、页数和解压后的内容流大小。

**理由**

这解决了 FR-008 表面上的矛盾：“识别文字”可以读取 PDF 中已经存在的文字层或 OCR 文字层，而“不处理 PDF 图片”则禁止把扫描像素渲染出来再执行 OCR。`pypdf` 是纯 Python 库，支持 Python 3.12，并且明确不负责图片 OCR。之所以需要资源限制，是因为压缩后的内容流在解压时可能占用极大的内存。

**考虑过的替代方案**

- PyMuPDF：增加了页面渲染和图片处理能力，同时存在 AGPL/商业授权方面的考虑。
- `pdfplumber`：适合复杂表格，但第一版的纯文字边界暂时不需要。
- OCRmyPDF/Tesseract：直接违反“不处理 PDF 图片”的决定。

**依据与来源**

- https://pypdf.readthedocs.io/en/stable/user/extract-text.html
- https://github.com/py-pdf/pypdf/releases/tag/6.16.1

## 8. 独立图片理解

**决定**

先用 Pillow 校验图片类型、尺寸和解压限制，再由当前 Agent 的视觉能力返回严格的文字结构：结果只能是 `usable`、`no_evidence` 或 `review`，并包含识别出的事实、省略内容和不确定之处。OCR 不作为主要处理路径。只有经过标注的验收图片集证明中文文字识别不足时，才考虑增加 PaddleOCR。

不能假设任意 Agent 的普通图片粘贴流程都符合附件边界。胶囊 Skill 必须使用受控的临时输入路径，并在成功、生成审核项或失败时清理系统创建的副本。Hermes 兼容性测试需要额外检查其图片缓存行为。

**理由**

单纯识别字符，无法判断图表、照片或流程图是否能够脱离外部上下文完整表达知识。当前 Agent 的视觉能力负责这种语义判断，Python 则校验输出结构和后续分流。Hermes 的标准图片粘贴流程会在 `~/.hermes/images/` 下写入 PNG 文件；这属于基座适配时必须验证和处理的差异，不能进入 Python 业务核心。

**考虑过的替代方案**

- 只使用 OCR：无法理解图形、关系和内容是否完整。
- 强制引入 PaddleOCR：在验收资料证明有必要以前，就增加了体积较大的推理依赖。
- 假设 Hermes 会自动清理上传文件：与当前图片来源实现不符。

**依据与来源**

- Hermes 视觉能力说明：https://hermes-agent.nousresearch.com/docs/user-guide/features/vision
- `/Users/apple/.hermes/hermes-agent/tools/image_source.py`
- Pillow 的解压炸弹防护机制。
- PaddleOCR 3.7.0 支持 Python 3.12：https://github.com/PaddlePaddle/PaddleOCR/releases/tag/v3.7.0

## 9. 音频与视频转写

**决定**

使用 `faster-whisper` 1.2.1，并开启语音活动检测。直接传入路径或 `BinaryIO`；PyAV 可以从音频或视频容器中解码音轨，因此第一版不创建中间音频文件，也不要求单独安装 FFmpeg 可执行程序。处理结果保留分段时间戳和质量信号；审核分流规则应通过有标注的中英文样例进行校准，而不是使用一个通用置信度阈值。

**理由**

`faster-whisper` 支持 Python 3.12，其 PyAV wheel 已包含 FFmpeg 库。分段的平均对数概率、无语音概率和时间戳，可以为有限重试或进入审核提供可测试的信号。

**考虑过的替代方案**

- OpenAI Whisper 包：速度较慢，并依赖系统级 FFmpeg。
- 云端语音识别：会增加 Brief 尚未确定的服务商、隐私和成本决策。
- WhisperX/说话人分离：区分说话人不属于第一版需求。

## 10. 网页获取与网页图片处理

**决定**

使用带资源限制的 `httpx` 流式请求获取网页，再用 `trafilatura` 2.2.0 提取正文和表格，并关闭图片输出。只在临时 DOM 中检查 `figure`、`figcaption`、`alt` 和邻近正文，以筛选可能包含独立信息的图片。装饰性图片和重复正文的图片直接忽略；确有必要的候选图片通过当前 Agent 的受控视觉路径处理，只持久保存转换后的文字。对于仅靠 JavaScript 渲染、需要登录或抽取结果为空的网页，第一版进入审核，不额外引入浏览器运行环境。

**理由**

`trafilatura` 提供的是正文抽取，而不只是原始 DOM 解析；它支持 Python 3.12，也能保留文字表格。受限的流式请求可以保护本地资源。暂缓浏览器自动化，可以避免引入第二套缓存和运行时生命周期，让第一版保持在已经确认的范围内。

**考虑过的替代方案**

- 只用 BeautifulSoup/lxml：它们是解析器，不是可靠的正文选择器。
- 使用 Playwright 兜底：后续可能有用，但依赖较重，还会引入浏览器及用户配置缓存。
- 保存图片 URL 以后再处理：SPEC 已明确禁止。

**依据与来源**

- https://github.com/adbar/trafilatura/releases/tag/v2.2.0
- https://github.com/adbar/trafilatura/blob/master/pyproject.toml

## 11. 临时附件生命周期

**决定**

采用以下文件归属规则：

- 用户拥有的本地路径只原地读取，系统绝不删除。
- 在资源限制允许时，PDF、图片和 HTML 数据优先放在内存中处理。
- 音频和视频直接使用 `BinaryIO` 或用户原始路径。
- 只有第三方库必须接收路径时，才在胶囊系统拥有的 `TemporaryDirectory` 中创建文件。
- 成功、生成审核项、异常、取消和超时都通过 `finally` 执行清理。
- 日志只记录类型、大小、哈希和处理状态，绝不记录附件字节、base64 或网页图片 URL。

突然发生 `SIGKILL` 或主机故障时，Python 无法保证执行 `finally`。第一版不为这种情况建设持久租约和启动恢复机制；运行指南必须如实说明这一限制，不能把操作系统临时文件描述为系统保存的证据。

**理由**

明确文件归属，既能防止系统误删用户原始文件，也能确保系统自己创建的临时副本不会变成隐藏的附件仓库。

**考虑过的替代方案**

- 删除所有输入路径：具有破坏性，也侵犯用户对原文件的所有权。
- 为以后审核保留缓存文件：违反附件不得持久保存的边界。
- 在流程完成前把附件放进 SQLite 或飞书：会把临时输入变成系统管理的证据。

**依据与来源**

- Python 3.12 `tempfile`: https://docs.python.org/3.12/library/tempfile.html
- Hermes 图片缓存行为见第 8 项决定。

## 12. 测试与验收策略

**决定**

使用 `pytest` 完成必要的单元测试、CLI 契约测试、内容提取样例、飞书适配测试和端到端验收。验收资料在执行前标注预期结果，并覆盖 SPEC 的关键成功标准。Plan 保留项目默认测试强度，不建立额外的测试治理系统。

**理由**

SPEC 中的 100% 指有限且预先标注的验收集。把资料保存为可重复执行的验收样例，可以避免把有限样例结果误写成模型对所有现实输入的准确率。契约测试还能把确定性规则与模型波动分开。

**考虑过的替代方案**

- 只进行人工对话测试：无法稳定复现，也难以检查不应该出现的持久化结果。
- 只进行单元测试：无法覆盖飞书写入与 Agent 契约漂移。
- 每次都运行真实 OpenAPI 测试：速度慢且容易受外部环境影响；应保留少量专用集成测试，并结合模拟或录制响应。

**依据与来源**

- `spec.md` 中的成功标准 SC-001 至 SC-015，以及其中关于有限验收集的假设。
- 阶段 1（Phase 1）的验证流程见：[quickstart.md](./quickstart.md)。
